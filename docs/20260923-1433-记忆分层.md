# 记忆分层：让 Agent 记住事

> 本文是 Agent 外壳八大组件系列第 3 篇。总览见 [20260923-1429-Agent本质.md](20260923-1429-Agent本质.md)。

---

## 一、一句话回答

**大模型 API 本身没有记忆——每次调用都是失忆重开。记忆系统用"分层存储"补上这块：短期记忆管当前会话，长期记忆管跨会话沉淀，向量库负责"想起来"。** 记忆层把 Agent 从"单次智能"升级为"累积智能"，这是它区别于普通聊天机器人的根本。

没有记忆的 Agent 有三类典型痛点：用户每次都要重复背景说明；Agent 反复踩同样的坑；决策前后矛盾。

---

## 二、一个医生的记忆（最好记的比喻）

- **短期记忆**：当前正在看的这位病人的症状描述
- **长期记忆**：10 年来积累的临床经验（"上次遇到类似症状，最终诊断是 XX"）
- **向量记忆**：看到症状能联想到相似病例（"这个症状组合让我想起 3 年前的一个病人"）
- **知识图谱**：医学知识网（"药物 A →禁忌→ 疾病 B"）
- **参数化记忆（模型权重）**：医学院学的教科书知识

没有记忆的 Agent，每次对话都从零开始——就像一个每天早上失忆的医生。

---

## 三、分层架构：不要把所有信息塞进一个篮子

很多团队的失败做法：一上来就对接向量数据库，把所有对话历史全塞进去，结果召回答非所问、状态混乱、检索性能崩掉。本质是混淆了不同记忆的定位。成熟的分层方案：

| 层级 | 存什么 | 用什么存 | 为什么 |
|---|---|---|---|
| **短期记忆** | 当前会话上下文、临时状态、工具返回 | 上下文窗口 / Redis（带 TTL） | 快，自动过期，服务当前任务 |
| **工作记忆** | 任务状态：做到哪一步、已试过什么 | 状态外置到数据库 | 任务不断片，可断点续跑 |
| **长期记忆** | 用户偏好、历史结论、沉淀经验 | 向量库（pgvector 等） | 跨会话"像不像"检索召回 |
| **团队记忆** | 规则、口径、共享知识 | 关系库/文档 | 结构化，权限清晰 |

各层生命周期不同：短期记忆高时效（当前轮次结束价值就下降），长期记忆要求可沉淀、可更新、可遗忘。

---

## 四、核心难点不是"存"，而是"写什么、何时写、怎么召回"

记忆设计的三个关键组件（比选哪个向量库重要得多）：

1. **提取器（Extractor）**：从对话流里自动识别什么值得存——关键词提取？还是让大模型做摘要和结构化？
2. **触发器（Trigger）**：什么事件触发写入（会话结束、用户明确指令）？什么事件触发读取（任务开始、遇到未知概念）？
3. **注入器（Injector）**：检索到的记忆以什么格式、多大篇幅、插入上下文什么位置？

很多记忆系统失败，不是因为没有向量库，而是**只做了"存"和"查"，没设计读写时机、记忆质量、冲突规则和验证机制**。

---

## 五、为什么不能靠"微调"来记事？

常见疑问：把用户偏好训进模型权重里行不行？**不行。** 参数化记忆是模型权重，微调成本高、更新慢（要重训），适合通用知识，不适合每个用户的个性化对话。外挂记忆（向量库+检索）才是当下商用主力路线——2026 年 5 月腾讯云开源 TencentDB Agent Memory（短期压缩、长期沉淀、团队共享三层），信通院把数据库定位成 AI Agent 的"长效记忆中枢"，说明这已是行业共识。

---

## 六、常见坑

1. **Demo 很好，一上生产就崩**：对话多几轮上下文溢出、召回答非所问——通常是没分层，全塞一个地方。
2. **只存不删**：记忆只进不出，过期偏好和已推翻的结论继续干扰决策。需要遗忘/淘汰机制。
3. **按会话隔离失败**：用户 A 的记忆串到用户 B，隐私事故。长期记忆必须按 session/user 严格隔离。
4. **记忆投毒**：恶意内容被写进记忆并长期污染决策——这也是安全问题（见[权限安全](20260923-1433-权限安全.md)）。

## 七、最新洞察："最好的记忆系统是 md 文档"——文件派 vs 数据库派

你听到的这个说法并非空穴来风。2025 下半年起，一个朴素到反直觉的范式确实赢了，业界总结为**"文件即真相"（files as truth）**。来看证据和边界。

### 先看事实：个人 / Coding Agent 集体倒向文件派

几乎所有 2025 年之后火起来的个人 Agent 都选了 Markdown 文件做记忆：Claude Code 的 CLAUDE.md、Codex 的 AGENTS.md + memories 目录、OpenClaw 的 MEMORY.md、Cursor 的 .cursor/rules、Copilot 的 copilot-instructions.md——无一例外。而坚持数据库派（mem0、Letta、Zep）的，主要是**把记忆当独立产品卖的记忆中间件**。

最硬的证据来自 Letta 的实验：**一个用 GPT-4o-mini 的简单文件系统 Agent，在 LoCoMo 记忆基准上拿到 74.0%，反而高于 Mem0 报告的最佳图变体的 68.5%**。结论耐人寻味：**记忆质量更多取决于 Agent 如何管理上下文，而非具体检索机制**——这正是本系列[上下文管理篇](20260923-1433-上下文管理.md)的核心论点。

### 为什么"土办法"反而有效？

| 优势 | 说明 |
|---|---|
| **人能看见** | 向量是一堆浮点数，md 文件直接打开就能读——Agent 记错了，删掉那一行即可 |
| **人能管** | 可以 code review、可以 git blame 出某条规则是谁哪天加的、可以在 PR 里讨论和回滚——记忆复用了开发者现成的工作流 |
| **天然时间顺序** | Markdown 保留时序，避免语义检索中的时间混淆 |
| **零外部依赖** | 不用养 Qdrant/Neo4j/pgvector 那套基础设施，调试就靠 cat 和 ls，迁移成本几乎为零 |
| **治理即工程** | 结论来源、是否过期、责任边界、纠错追源——这些治理动作全变成普通工程动作：可读、可 diff、可 commit、可审计 |

### 但别过度夸大——文件派的三个硬约束

1. **容量天花板**：一个 MEMORY.md 不可能无限膨胀。文件派靠"常驻精简索引 + 明细按需读"续命，而这套技巧本身就是为了绕开"人能读的文件装不下太多"的硬约束。
2. **前提是"提炼后的自然语言"**：文件派几乎没人纯靠 append——人要读，就得先提炼。往里塞原始对话流水账，"可读"优势名存实亡。
3. **检索能力弱**：规模一大就乱。个人/单 Agent 场景成立；多租户、大容量、强语义检索的企业级场景，数据库派仍是答案（Oracle 甚至专门发研究论证"Agent 记忆是个数据库问题"）。

### 我的洞察：这不是"谁更好"，而是"读者是谁"

业界规律已经相当一致：**个人 Agent 选文件派，记忆中间件选数据库派**。但 2026 年更值得注意的方向是**混合派**：字节开源的 OpenViking 把记忆组织成虚拟文件系统（可用 ls/tree/find 像浏览文件一样浏览上下文，检索可观测可 debug），内部用向量定位目录再逐层下钻；ai-memory 项目用 Markdown 做**事实来源**（source of truth），SQLite 只做派生索引（全文检索 + 词法匹配），备份就是 git clone。

一句话总结这个说法的适用边界：**当记忆的读者同时包括人和 Agent、且规模在个人到团队级时，md 文档 + git 就是最好的记忆系统；当规模和检索复杂度超出"人能浏览"的范围时，向量库/图数据库重新接管。** 你现在看的这个 docs/ 目录，正是文件派记忆的活样本——它就是 microgpt 项目和我之间共享的长期记忆。

---

## 八、回到 microgpt

microgpt 完全无记忆系统——input.txt 一次性读入，训练完就固定。它的"记忆"全部烧在几千个参数里（参数化记忆的最小样本）。工业 Agent 的做法正好相反：**参数不动，把会话、偏好、状态全部外挂**。一个是"把经验长进脑子里"，一个是"随身带笔记本"。
