# Windows + 统信UOS 双平台适配成本评估

> 背景：自研 Agent 需要同时支持 Windows 和 统信UOS（信创场景），评估开发与适配成本。

---

## 一、先确认关键前提：统信UOS 跑在什么 CPU 上？

统信UOS（UnionTech OS）本身基于 Debian，用 `apt` 包管理，桌面环境是 UKUI。
**但它最大的成本变量不是"统信"这个 OS，而是它下面配的 CPU 架构**：

| 场景 | 常见 CPU | 架构 | 适配难度 |
|---|---|---|---|
| 普通统信 x86 | 兆芯 / 海光 | x86_64 | 低（等同普通 Linux） |
| 国产 ARM | 飞腾 / 鲲鹏 | aarch64 | 中（native 依赖要重编） |
| 国产 LoongArch | 龙芯 | loongarch | 高（生态最不成熟） |

**在开始写代码之前，务必先确认目标部署机器的 CPU 架构。** 这一步直接决定后面 80% 的成本量级：
- 只跑 x86_64 的统信 → 本质上就是"再支持一个普通 Linux"，成本可控
- 要跑飞腾/龙芯 → 所有带 C 扩展的依赖、native 二进制都要重新编译/交叉编译，成本明显上升

---

## 二、成本取决于你的 Agent 形态

结合上一轮讨论的"自研 agent"方向，按形态分三档：

### 形态 A：纯后端 / 命令行 Agent（无 GUI）——成本：低
- Python（如当前 microgpt）跨平台性好，Windows/Linux 基本通用
- 主要工作量：
  - 路径分隔符、换行符（`\n` vs `\r\n`）差异处理
  - 系统命令双实现（PowerShell vs bash）
  - 若有 native 扩展（如某些音视频、加密库），需为 aarch64/loongarch 重新编译
- 结论：如果 agent 无强 GUI 需求，这是最省事的路线

### 形态 B：桌面客户端（Electron / Tauri）——成本：中~高
- **Electron**：对统信支持度一般，需要 Linux 版 `.deb` 包，且要在目标 CPU 架构上编译 Node 依赖；统信 UKUI 桌面与主流桌面有差异，系统 API / UI 可能有坑
- **Tauri**（Rust）：交叉编译成熟度更好，整体比 Electron 省，但 `loongarch` 支持是后加的，需要验证
- 共同成本：双平台打包分发（`.exe` + `.deb`）、目标架构 CI 构建
- 结论：如果一定要桌面客户端，建议选 Tauri，并且**先做一轮"统信 + 目标架构"的可行性验证**再全量投入

### 形态 C：本地引擎 + Web 前端（推荐折中）——成本：低
- 复用浏览器当前端，Windows 和统信都能直接访问 `localhost`，不用做双套 GUI
- 后端跨平台，只需处理系统命令差异
- 结论：三者中成本最低、收益最高，适合作为首选方案先跑通产品价值

---

## 三、共性成本项清单（无论选哪种形态都要做）

1. **路径 / 换行符 / 编码差异**：统一用 `os.path` / `pathlib`，避免硬编码 `\`
2. **系统命令双实现**：把 `shell` 命令按平台分发（Windows 走 cmd/PowerShell，Linux 走 bash）
3. **native 依赖跨架构编译**：列出所有带 C 扩展的依赖，确认目标架构有对应 wheel，没有则自建
4. **打包 / 分发**：Windows 出 `.exe`/安装包，统信出 `.deb`；在 CI 里做双平台构建
5. **信创合规**：等保、密评、对接国产数据库/中间件（如有）——这部分容易被低估，要提前确认甲方/采购方要求
6. **国产 CPU 架构适配**（aarch64 / loongarch）：**最容易低估的成本项**，务必在第一阶段就做小范围验证

---

## 四、结论与建议

1. **先定前提**：确认统信目标机器的 CPU 架构（是否信创 CPU），这是成本的分水岭
2. **选形态**：如果 agent 无强 GUI 需求，优先 **"本地引擎 + Web 前端"**，成本最低、双平台覆盖最顺
3. **做验证**：在投入全量开发前，先在目标架构的统信机器上跑一个最小可行版本（能启动、能调用核心 agent 能力），验证 native 依赖与命令分发没有问题
4. **打包统一进 CI**：Windows + 统信（多架构）构建放在流水线里自动化，避免手工重复
5. **信创合规单独排期**：等保/密评/国产中间件对接是独立一条线，不要和业务开发混在一起估算

> 一句话总结：**"Windows + 统信"里真正的成本大头是"国产 CPU 架构适配"和"信创合规"，而不是"统信这个 OS"本身。只要确认目标 CPU 架构并选定"本地引擎 + Web 前端"的形态，整体开发成本是可控的。**
