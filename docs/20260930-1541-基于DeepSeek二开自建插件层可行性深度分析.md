# 基于 DeepSeek 二开，自建插件层可行性深度分析

> 问题：如果我要基于 DeepSeek 来二开，是否可以自己做一个插件层？
> 结论先行：**可以，而且官方机制本就是为"自由组合插件"设计的**——但要先想清楚你要的"插件层"是哪一层。DSH 已经自带一套完整的插件机制，"再造一层"在多数情况下是重复造轮子；真正值得自建的是**治理层 / 分发层 / 集成层**，而不是能力扩展层。
> 本文基于 DeepSeek Harness (DSH) 开发者预览版 + Cordis 插件框架 + 插件市场 cordis.run 的公开资料写成。

---

## 一、先厘清："二开"有四种含义，总评分完全不同

| 路径 | 含义 | 可行性 | 推荐度 |
|---|---|---|---|
| **A. 官方插件（Bundle）** | 不碰源码，写声明 `dsh.bundle` 的 npm 包扩展能力 | ✅ 官方主推通道 | ⭐⭐⭐⭐⭐ |
| **B. 治理插件层（meta layer）** | 在 DSH 之上再包一层：插件注册表、审批、签名、模型网关、审计 | ✅ 可行，本身也是一个 Bundle | ⭐⭐⭐（有明确治理需求才做） |
| **C. Fork 源码** | 拉源码改插件层/换壳 | ⚠️ 可以但代价高 | ⭐⭐（仅推荐"套壳分发"） |
| **D. 完全自研 + 接 DeepSeek 模型** | 自己写 agent 底座，DeepSeek 只是可替换的模型后端 | ✅ 最自由，成本最高 | ⭐⭐⭐（DSH 复杂度超出需求时选） |

**一句话**：想扩展能力 → 走 A；想做企业治理/收口 → 走 B；想改产品形态/分发 → 走 C；想彻底自主 → 走 D。

---

## 二、DSH 已有的插件机制盘点（你做插件层的地基）

"基于 DeepSeek 二开"之前，必须知道官方已经给了你什么：

### 2.1 插件形态与安装
- **插件定义**：一个"声明了 `dsh.bundle` 的 npm 包"（A cordis plugin is an npm package declaring `dsh.bundle`）
- **安装命令**：`dsh plugin --profile web add <package>`，以 pnpm 依赖装入 profile 目录，并自动 reconcile 进 `dsh.profile` 的 bundles 列表
- **安装保护**：client gate + profile lock + 完整性验证，安装后需重启 session 生效
- **发布渠道**：官方插件市场 `cordis.run`（已收录约 349 个插件、6 大分类），提交 npm 包名 + 仓库链接，校验 `dsh.bundle` 声明 + 人工审核
- **Python 侧**：官方 `deepseek-harness-sdk`（Python 3.10+），与 TypeScript SDK 共享同一套 profile / patch 机制

### 2.2 "一切皆插件"的可替换接缝（Seams）
模型、工具、技能、会话、沙箱、存储全部可替换重组，核心 `ctx` 服务键：

| Seam | `ctx` 键 | 你能做什么 |
|---|---|---|
| 模型适配 | `ctx.llm` | 换模型后端、多模型路由、私有模型接入 |
| 工具系统 | `ctx.tools` | 注册新工具、审批拦截（pre/execute/post 三步流水线） |
| Agent 接口/主循环 | `ctx.agents` / `ctx.agentLoop` | 替换 agent loop 本身（可热替换） |
| 会话日志 | `ctx.sessions` | 事件溯源、可重放、审计 |
| 沙箱 | `ctx.sandbox` | 远程沙箱迁移（Bash/PTY/LSP 一并迁移） |
| Webhook | `ctx.webhookRuntime` | 外部事件驱动会话 |
| 会话投影 | `ctx.sessionProjections` | 自定义载体/宿主视图 |
| Agent Teams | `ctx.agentTeams`（实验性） | 多 Agent 协作（roster/任务板/mailbox） |

### 2.3 装配体系：Profile + Bundle + Patch 叠加
```
空条目列表 → profile 列出的组合包（按序叠加）→ profile 的 cordis.patch.yml → home 级 patch → --patch overlay
```
你想注入的定制行为，**优先用 patch 叠加，而不是改源码**。

### 2.4 模型不锁定（对二开最关键）
DSH 支持 `settings.yaml` 配置**自定义 provider**（字段：`apiKeyEnv`、`api`、`baseURL`、`models`），官方预置 Anthropic、OpenAI 两个内置 provider。DeepSeek 后端对你而言只是**可替换的一层**——这既是机会（随时把模型收口到自有网关），也意味着"基于 DeepSeek 二开"其实"基于的是 DSH 这个 Harness"，DeepSeek 模型和 Harness 要分开谈。

## 三、关键判断：你到底还需不需要"自己做一个插件层"？

### 3.1 如果你的目标是"给 agent 加能力"——不需要
写工具、加 hook、换模型、加界面，官方 Bundle 机制已完整覆盖。再造一层插件层 = 重复实现加载/卸载/注册表，且要跟 Cordis 的上下文、事件、副作用可逆语义对齐，纯负担。

### 3.2 只有以下诉求，才值得自建一层
1. **企业内部插件治理**：私服 registry、白名单、签名校验、审批流——公开市场（349 个插件、多为早期预发布、多数未审计）不能满足企业内控
2. **模型网关收口**：把 `ctx.llm` 统一收到公司网关（鉴权、审计、计费、多模型路由、私有模型），而不是让每个 agent 实例各自直连
3. **多租户 / RBAC / 数据隔离**：DSH 的 scope 隔离是"按 agent"的，租户级隔离要自己包
4. **合规审计上报**：等保/信创场景下，需要把会话事件流转成审计日志外发
5. **版本锁定与灰度**：市场插件迭代极快，官方都提示必须锁版本号（`@latest` 会踩坑），企业分发需要统一版本策略
6. **内嵌分发**：把 DSH 装进自己的产品壳里分发（典型如 Skyearn/deepseek-harness-app 套原生壳）

**核心结论：DSH 的插件机制解决"能力层"，不解决"治理层、分发层、租户层、集成层"。你自建插件层的真正价值在后者。**

## 四、路径 A：官方 Bundle 插件（首选举措）

### 4.1 做法
在你的 npm 包里声明 `dsh.bundle`，插件向 `ctx` 贡献服务、事件监听与副作用，通过 `dsh plugin add` 或 patch 层进入 profile。典型内部插件：

- `model-gateway`：把 `ctx.llm` 指向公司网关（OpenAI 兼容协议 + 自有鉴权），实现"实例不感知模型来自哪"
- `audit-sink`：监听 `turn/*`、`tool/*` 会话事件，落审计库
- `approval-policy`：在 `tools/pre-execute` 事件上加公司审批规则
- `tool-whitelist`：按角色收窄 `ctx.tools`

### 4.2 评估
- **优点**：不 fork、上游升级可跟进；MIT 协议可自由商用（保留版权声明）；卸载即撤销（Cordis 副作用可逆）
- **缺点**：受限于 DSH 提供的 seam 和事件——没有 seam 的地方（如深层 UI 改造、agent loop 语义变更）改不动，只能等官方或走 C/D
- **工作量**：单个插件 1–3 人周；4 个内部插件约 1–2 人月

---

## 五、路径 B：DSH 之上的"治理插件层"（插件的插件）

### 5.1 定位
你的插件层**本身也是一个 Bundle**（meta layer），向下管 Cordis，向上对业务团队提供托管：

```
┌─────────────────────────────────────┐
│  业务插件（各部门自研 bundle）          │
├─────────────────────────────────────┤
│  治理插件层（你自建，本身是一个 bundle）  │
│  · Plugin Registry（私服+白名单）       │
│  · Manifest 规范（能力/权限/依赖/版本）   │
│  · 生命周期管理 install→load→enable    │
│    →disable→unload（幂等可逆）          │
│  · 签名/完整性校验（fail-closed）        │
│  · 版本锁定与灰度                        │
│  · 审计事件外发                          │
├─────────────────────────────────────┤
│  DSH（Cordis：ctx / 事件 / patch 叠加）  │
├─────────────────────────────────────┤
│  DeepSeek / 其他模型 provider          │
└─────────────────────────────────────┘
```

### 5.2 设计要点
- **注册表**：私有 npm registry（或 git monorepo + 内部索引），`dsh.bundle` 声明作为机器可校验的准入条件
- **Manifest**：在 `dsh.bundle` 之外扩展自己的元数据字段（所需 seam、权限声明、兼容 DSH 版本、签名）
- **生命周期**：映射到 Cordis 的挂载/卸载语义；必须实现 onDispose 清理（Cordis 的副作用可逆是你的朋友也是约束——注册了什么就要能撤什么）
- **完整性**：安装时校验签名与哈希；市场插件迭代快，一律锁版本
- **审计**：复用 DSH 事件流（"模型可见即已记录"原则），转成企业审计格式外发

### 5.3 诚实提醒
多数团队**并不需要**这一层——先数数你们未来一年会有几个内部插件、要不要跨团队分发、要不要过等保。数量 < 5 且不涉密，用 Git 仓库 + patch 文件手工管理就够。

## 六、路径 C：Fork 源码（唯一体面的姿势是"套壳"）

### 6.1 现实案例：Skyearn/deepseek-harness-app
官方 DSH 的 fork，做法是"**保留 web 运行器不动，原生壳只管托管界面、进程和运行时，功能扩展全部交给插件生态**"：
- Swift 原生 + WKWebView 承载 `dsh web` 界面；退出即终止服务、释放端口（不留孤儿进程）
- 捆绑裁剪版 Node.js，zip 解压即用
- 中文本地化、单实例、崩溃恢复

这印证了二开的正确姿势：**fork 只做"壳与分发"，能力扩展仍然走官方插件层**。直接 fork 改插件层源码，会立刻背上三个包袱：预览版契约频繁变更、合并上游困难、官方明示的"未经安全审计"，且维护成本全在你这边。

## 七、路径 D：完全自研 + DeepSeek 模型（呼应 microgpt）

### 7.1 什么时候选自研
- DSH 的复杂度超出需求（社区共识：日常写代码并不需要 Cordis 的复杂度）
- 要深度定制 agent loop / 自改写运行时
- 双平台（Windows + 统信 UOS/国产 CPU）分发，不想被 Node/pnpm 生态绑定（UOS + 飞腾/龙芯下原生依赖编译是已知的坑）
- 需要把 agent 嵌进自己的产品成为功能模块，而非卖工具本身

### 7.2 自研插件层设计要点（可直接落地的精华清单）
1. **Manifest 规范**：能力声明、权限、依赖、兼容版本、签名
2. **生命周期**：install / load / enable / disable / unload，全部幂等且可逆（学 Cordis：副作用可逆）
3. **Context 服务注册**：`tools / hooks / settings / storage`，插件向上下文注册而非改代码
4. **事件总线**：事件命名对齐 DSH（`turn/*`、`step/*`、`tool/*`、`agent/*`、`llm/stream`），**未来插件可双向移植**，大幅降低锁定风险
5. **沙箱与权限**：默认拒绝（fail-closed）；进程级沙箱（可借鉴 `sandbox-micro` 的 microVM 思路或 OS 级方案）；工具执行三步流水线 pre/execute/post
6. **版本与完整性**：签名 + 哈希校验，一律锁版本
7. **事件溯源审计**："模型可见即已记录"——会话可重放、可 fork、可审计，这是 DSH 最值得抄的一条
8. **Profile 化多模式**：标准 / 极简 / 创造 多模式叠加（学 DSH 的 Ordered Config Layer）
9. **seam 抽象模型后端**：OpenAI 兼容协议 + provider 抽象，DeepSeek 只是其中一个 provider，随时可替换（学 DSH 的 `settings.yaml` 自定义 provider）

### 7.3 工作量参考
MVP（manifest + 生命周期 + 上下文 + 事件 + 3 个示例插件）：约 3–6 人月；加上沙箱与治理约再翻一倍。**对比路径 A 的 1–2 人月，自研贵 5–10 倍**——除非战略上必须自主，否则不划算。

## 八、选型矩阵

| 维度 | A 官方插件 | B 治理层 | C Fork | D 自研 |
|---|---|---|---|---|
| 初期成本 | 低（1–2人月） | 中（2–4人月） | 中高（壳）+ 长期维护 | 高（6–12人月） |
| 控制力 | 受限于 seam | 高（治理面） | 最高（源码级） | 最高 |
| 上游升级跟进 | ✅ 最好 | ✅ 好 | ❌ 经常冲突 | 无关 |
| 锁定风险 | 中（用 seam 可降） | 中 | 高 | 低 |
| 安全合规可控 | 依赖官方（未审计） | ✅ 可补齐 | ✅ 但自维护 | ✅ |
| 双平台(UOS/国产CPU)适配 | 中（Node 链） | 中 | 中 | 最好（可选技术栈） |
| 适合阶段 | 验证期→ Production | 企业内推广期 | 产品化分发期 | 战略自主期 |

## 九、推荐路线图（结合 microgpt 与双平台背景）

- **Phase 1（1–2 人月）**：先不造层。装 DSH，用官方 Bundle 写 2–3 个内部插件（`model-gateway` + `audit-sink` + `approval-policy`）验证 seam 够不够用。**这是最便宜的信息收集**。
- **Phase 2（2–4 人月）**：复盘 Phase 1 的卡点。若卡点是治理/分发/租户而非常规能力，再做 B 治理插件层（本身以 Bundle 形态存在，卸载可逆，试错成本低）。
- **Phase 3（决策点）**：若 DSH 的复杂度、Node 生态或预览版不稳定性严重拖累双平台落地（尤其 UOS + 国产 CPU），迁向 D 自研轻量底座——Phase 1/2 沉淀的插件用"事件命名对齐"的约定平移，迁移成本可控。
- **明确不做**：除非要出独立产品壳（学 Skyearn），否则不 fork 源码。

### 决策检查点
1. 内部插件预计 > 5 个且跨团队？→ 考虑 B
2. 要过等保/信创、多租户？→ 必须 B（DSH 未审计，不能裸奔）
3. 目标机器是 UOS + 飞腾/龙芯？→ 提前在真机跑通最小验证，否则慎重 A/B
4. agent loop 要深度自研语义？→ 直接 D
5. 只是想要个自研 agent？→ A/D 二选一，别碰 C

## 十、风险与注意事项

1. **许可**：DSH 为 MIT，可自由商用/修改，但须保留版权声明；二次开发（含 fork）遵守 MIT 条款
2. **预览版风险**：DSH 处于 developer preview，API、事件契约、命令可能随版本变更，插件要锁版本
3. **安全红线**：官方明示预览版**未经安全审计**，Sandbox / Approval / Permission **不构成完全隔离保证**；生产环境务必经治理层补齐或自行评估
4. **市场插件质量参差**：349 个插件多为早期预发布、多数未审计；GitHub 源插件安装会触发在 agent 沙箱**之外**执行的构建脚本——先审源码，锁版本，默认拒绝
5. **成本在模型不在插件**：插件本身免费开源，真实成本是模型 API 调用额度；自建 model gateway 的动机之一正是把成本管起来
6. **双平台适配**：Node/pnpm 依赖链在 UOS + 国产 CPU（飞腾/龙芯）上编译原生模块是主要坑；评估 B/A 之前先在目标架构真机验证
7. **反模式**：为了"掌控感"一上来就 fork 改源码——升级困难和审计缺口会长期反噬
