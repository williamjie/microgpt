# Agent Loop：Agent 的心跳

> 本文是 Agent 外壳八大组件系列第 1 篇。总览见 [20260923-1429-Agent本质.md](20260923-1429-Agent本质.md)。

---

## 一、一句话回答

**Agent Loop（执行循环）就是让大模型反复执行"思考 → 行动 → 观察"，直到任务完成或触发终止条件。** 它是 Agent 最核心的运行机制——业内有个说法：几乎所有 Agent 系统，无论包装得多复杂，内核都能还原成这个循环。这个范式有个专门的名字：**ReAct**（**Rea**soning + **Act**ing，推理+行动）。

为什么说它是"心跳"？因为大模型 API 本身是无状态的、一次性的——看一眼文字，回一段话，结束。是循环把它变成能连续干活的系统。

---

## 二、循环的四个步骤

1. **接收输入**：拿到用户请求或上一轮的观察结果，组织进上下文
2. **思考（Think / Reason）**：模型基于当前上下文判断下一步——调工具？直接回答？还是需要更多信息？
3. **行动（Act）**：如果决定调工具，系统真正执行，拿到结果。**注意：执行的是外部程序，不是模型**（详见 [工具调用](20260923-1433-工具调用.md)）
4. **观察（Observe）**：把工具返回的结果追加进上下文，回到第 2 步

```
┌──────────────────────────┐
│  1.思考（LLM）→ 2.行动（工具）→ 3.观察（结果）  │
│        ▲_____________回到 1_____________│
└──────────────────────────┘
        ↓ 终止条件满足
     最终结果
```

---

## 三、为什么这个循环有效？——外部反馈纠偏

对比纯 CoT（思维链）：CoT 只在模型"脑子里"推理，第一步的假设错了，就一路错到底。

ReAct 的本质优势是：**用真实观察打断错误链条**。模型假设"这个订单应该已发货"，工具返回"待付款"，错误假设立刻被拉回正轨。工具报错也不一定是坏事——它可能在告诉模型：路径错了、参数不全、权限不够。

**比喻**：走一步看一步的探路者，而不是出发前画好全程地图的规划者。当然"先规划再执行"（Plan-and-Execute）也是另一种范式，两者各有适用场景。

---

## 四、循环什么时候停？——最关键的设计问题

不知道什么时候停，就会无限循环。常见的终止条件有四种：

| 终止条件 | 说明 |
|---|---|
| 任务完成 | 模型判断信息充足，输出最终答案 |
| 达到最大步数 | 硬性上限，到点强制总结当前进展 |
| 超时/预算耗尽 | 时间或 Token 预算用完 |
| 失败升级 | 连续失败后升级给人工处理 |

这是 Agent Loop 从"Demo 十行代码"到"生产级系统"的分水岭。面试手撕 ReAct，评分点不在主流程，而在**边界处理**：轮数上限、解析失败、工具不存在、参数错误、重复调用、如何收尾。

---

## 五、常见坑

1. **死循环**：反复调同一个工具、在不同参数间震荡。成熟系统会做循环指纹检测（连续 N 步动作高度相似就强制中断）。
2. **烧 Token**：没有步数上限的 Agent，一个失败任务能把调用配额和钱一起烧光。
3. **串行瓶颈**：Loop 范式每轮只能调一个工具、等结果再走下一步——5 个互相独立的调用也得排队。需要并行时就得靠编排（详见 [Agent编排](20260923-1433-Agent编排.md)）。
4. **"模型太笨"的错觉**：很多翻车不是模型问题，而是"循环缺约束"。

---

## 六、回到 microgpt

generate() 的自回归循环就是 Agent Loop 的雏形：每生成一个 token，拼回输入，再生成下一个。Agent Loop 只是把"生成下一个 token"换成"生成下一步行动"，把"拼回输入"换成"把工具结果拼回上下文"。**Agent 没有魔法，它就是自回归循环 + 工具 + 记忆管理。**
