## 0. 目标与金融硬约束

信贷风控 Agent 系统要同时满足四条互相拉扯的硬约束：

1. **毫秒级快路径**：实时反欺诈、限额校验，交易进行中要给出信号，不能等深度推理。
2. **深度慢路径**：复杂授信（大额、多头、异常画像）需要多 Agent 协同推理 + 证据链。
3. **全流程可审计**：每个决策节点、每次工具调用、每个模型输出、人工介入都要留痕，可回放。
4. **数据不出域**：交易/征信/客户数据私有化，向量库本地（ES/Milvus），不上公共云。

**设计核心**：用"**快慢双模 + 路由**"把 1 和 2 解耦，用"**多 Agent 投票 + 证据留痕**"满足 3 和 4。

## 2. 双模执行引擎详解

金融版的"双模执行"指：**同一个 Agent 系统同时具备快、慢两种执行模态**，由 Router 按信号切换。

### 2.1 快路径（毫秒级，跑在实时交易旁路）
- **做什么**：反欺诈规则（设备指纹、异地、高频、黑产名单）+ 轻量评分模型（GBDT/轻量 LLM）+ 硬限额校验。
- **特点**：无 LLM 长推理，响应 < 100ms（对应金融版"100ms 弹性沙箱"能力）；输出是**信号**（放行/拦截/转慢路径），不是最终授信。
- **为什么必要**：实时交易不能等深度推理，快路径先挡掉 80% 的明显欺诈与超限。

### 2.2 慢路径（秒级~十秒级，多 Agent 深度协同）
- **做什么**：大额、多头借贷、异常画像、快路径存疑的申请，触发多 Agent 投票做证据化决策。
- **特点**：可调用工具（查征信、拉流水、检索政策库 RAG），产出**决策 + 证据链**。
- **为什么必要**：复杂授信需要"多个视角独立评估再聚合"，比单一模型更可解释、更可追责。

### 2.3 路由判定（快→慢 的触发条件）

| 触发条件（示例，机构自定义） | 走向 |
|---|---|
| 命中硬规则黑名单 / 超限额 | 快路径直接拦截 |
| 常规小额、画像正常 | 快路径出信号即完成 |
| 金额 > 阈值 / 多头借贷 ≥ N / 快路径评分落在灰区 | **转慢路径**多 Agent 投票 |
| 快路径置信度低（|score-0.5| < ε） | 转慢路径复核 |

**关键**：路由本身也要**留痕**（为什么这次走了慢路径），审计时能还原"信号来源"。

## 3. 多 Agent 投票机制详解

### 3.1 子 Agent 角色（各自独立、互不通气，避免"一个偏见传染全场"）

| Agent | 职责 | 主要工具/数据 | 输出 |
|---|---|---|---|
| **反欺诈 Agent** | 判断是否欺诈/团伙 | 设备指纹、图谱关系、黑产库 | 欺诈概率 + 证据 |
| **授信评估 Agent** | 还款能力/意愿 | 征信、流水、负债、行业 | 评分 + 建议额度 |
| **合规检查 Agent** | 是否符合监管/政策 | 政策库 RAG、客户分层 | 合规通过/阻断 |
| **限额/集中度 Agent** | 授信集中度、敞口 | 组合数据、集中度模型 | 限额余量 + 敞口告警 |

### 3.2 投票策略（三种可组合）

1. **多数表决**：≥ 2/4 同意放行。简单但会漏掉"少数派的强反对"。
2. **加权投票**：按 Agent 历史准确率加权（反欺诈 Agent 在欺诈样本上权重高，合规 Agent 在合规项上一票权重高）。
3. **一票否决（Veto）**：**合规 Agent 阻断 = 直接阻断**（监管红线不可被多数覆盖）；限额 Agent 判定超集中度 = 阻断。

推荐组合：**加权多数 + 合规/限额一票否决**。既利用加权提高精度，又守住"红线不被多数稀释"的合规底线。

### 3.3 冲突处理（Agent 之间结论打架怎么办）

- **一致性检测**：投票前算结论离散度。若 4 个 Agent 结论方差大（比如授信说"能批 50 万"、限额说"最多 10 万"）→ **不强行取均值**，而是标记"冲突"，升级人工，且**把冲突本身记入审计**（冲突说明证据不足或数据异常，是重要的风控信号）。
- **证据对齐**：冲突时先做一轮"交叉取证"（让相关 Agent 用 RAG 检索同一政策条款/数据源再复判），仍冲突才上人工。
- **禁止静默合并**：任何 Agent 的反对意见必须原样保留在决策证据链里，不允许聚合器"平均掉"。

## 4. AgentScope 2.0 风格伪代码（Python，供参考）

> 以下为**设计参考伪代码**，API 名称以 AgentScope 2.0 实际版本为准（2.0 已把 `ReActAgent` 重构为新的 `Agent` 类、用 `reply_stream` 流式）。重点表达"双模路由 + 多 Agent 投票 + 全链路留痕"的编排思想。

```python
from agentscope.agents import Agent
from agentscope.models import OpenAIChatModel
from agentscope.message import Msg
from agentscope.toolkit import Toolkit, register_tool
from agentscope.pipeline import sequential_pipeline, broadcast
from agentscope import memory, audit   # 审计/留痕（示意）

# ---------- 工具（每个 Agent 能调用的证据获取能力） ----------
@register_tool
def query_credit_report(customer_id: str) -> dict: ...     # 征信
@register_tool
def fetch_cashflow(customer_id: str, months: int) -> dict: ...  # 流水
@register_tool
def graph_neighbors(customer_id: str) -> list: ...           # 关联图谱(团伙)
@register_tool
def rag_policy(keyword: str) -> list: ...                     # 政策库检索(本地 RAG)
@register_tool
def check_exposure(customer_id: str) -> dict: ...              # 集中度/敞口

# ---------- 子 Agent（独立、互不通气） ----------
def make_agent(name: str, system_prompt: str, tools: list) -> Agent:
    toolkit = Toolkit(tools=tools)
    return Agent(name=name, sys_prompt=system_prompt,
                 model=OpenAIChatModel(...),   # 私有化部署的模型
                 toolkit=toolkit)

fraud_agent   = make_agent("反欺诈", "只判断欺诈/团伙，输出概率+证据",
                           [graph_neighbors, rag_policy])
credit_agent  = make_agent("授信评估", "评估还款能力/意愿，输出评分+建议额度",
                           [query_credit_report, fetch_cashflow])
compliance_agent = make_agent("合规", "判定是否违反监管红线，可一票否决",
                              [rag_policy])
limit_agent   = make_agent("限额集中度", "判定额度余量与敞口，可一票否决",
                           [check_exposure])

# ---------- 全链路留痕：每个 Agent 的输入输出都落审计 ----------
def audit_step(trace_id, agent, inp, out):
    audit.record(trace_id, agent.name, input=inp, output=out)

# ---------- 快路径（毫秒级，规则+轻量模型，非 LLM 长推理） ----------
def fast_path(req, trace_id):
    signals = []
    if req.device_blacklisted():            signals.append("拦截: 黑产设备")
    if req.amount > hard_limit(req):        signals.append("拦截: 超限额")
    if fraud_score_light(req) > 0.9:        signals.append("拦截: 欺诈分高")
    # 常规/灰区 → 返回信号，灰区升级慢路径
    escalate = (fraud_score_light(req) in GRAY_ZONE
                or req.amount > SLOW_THRESHOLD
                or req.multi_loan_count >= N_MULTI)
    audit_step(trace_id, "Router", req, {"escalate": escalate})
    return escalate, signals

# ---------- 慢路径（多 Agent 并行取证后投票） ----------
async def slow_path(req, trace_id):
    ctx = Msg("客户:" + req.summary())
    # 并行取证（broadcast：同一输入广播给各子 Agent，各自独立结论）
    results = await broadcast([fraud_agent, credit_agent,
                               compliance_agent, limit_agent], ctx)
    for a, r in zip([fraud_agent, credit_agent, compliance_agent, limit_agent], results):
        audit_step(trace_id, a, ctx, r)          # 每个结论留痕

    votes = parse_votes(results)                  # 各 Agent 的 {结论, 置信度, 证据}

    # 一票否决：合规/限额红线不可被多数覆盖
    if any(v.veto for v in votes if v.name in ("合规", "限额集中度")):
        decision = "阻断"
        return finalize(req, trace_id, decision, votes, reason="一票否决")

    # 加权多数表决
    weight = hit_rate_weight()                   # 按各 Agent 历史准确率加权
    score = sum(v.weight * v.loan_score for v in votes)
    decision = "放行" if score >= PASS_LINE else "拒绝"

    # 冲突检测：结论离散度过大 → 不静默合并，升级人工
    if conclusion_dispersion(votes) > CONFLICT_EPS:
        decision = "人工复核"
    return finalize(req, trace_id, decision, votes, reason="加权多数/冲突")

def finalize(req, trace_id, decision, votes, reason):
    audit.commit(trace_id, request=req, votes=votes,
                 decision=decision, reason=reason)   # 全链路可回放
    return decision

# ---------- 总编排 ----------
async def risk_pipeline(req):
    trace_id = audit.start(req)
    escalate, signals = fast_path(req, trace_id)
    if not escalate:
        return finalize(req, trace_id, "放行/拦截(快路径)", signals, reason="快路径信号")
    return await slow_path(req, trace_id)
```

**伪代码要点**：
- `broadcast` 让各子 Agent 拿**同一输入独立出结论**，避免偏见传染（对应 3.1）。
- 一票否决写在加权之前——**合规/限额红线优先于精度**（对应 3.2 推荐组合）。
- 冲突不静默合并，走人工并把冲突记审计（对应 3.3）。
- 每个 `audit_step` / `commit` 保证"可回放"，落地金融版的全链路审计。

## 5. 合规与审计（金融版能力映射）

| 金融合规要求 | 本设计如何满足 | AgentScope 支撑 |
|---|---|---|
| 全流程可追溯/可问责 | 每步 `audit.record` + 最终 `audit.commit`，冲突也留痕 | 金融版全链路审计回放 |
| 不接受黑箱 | 每个 Agent 输出"结论+置信度+证据"，证据引用 RAG 政策条款 | 事件流 + 证据对齐 |
| 数据不出域 | 模型私有化、RAG 走本地 ES/Milvus、工具只连内网数据源 | 金融版本地部署 + 开放源码定制 |
| 人工可介入 | 冲突/边界自动升级人工，介入动作本身留痕 | 金融版人工介入节点 + 留痕 |
| 低延迟不被拖垮 | 快路径毫秒级旁路，慢路径只处理该处理的 | 100ms 弹性沙箱 |

## 6. 部署形态

- **私有化**：整套（模型 + 向量库 + 数据源 + Agent 编排）部署在机构内网，`AgentScope 金融版`开放源码便于合规改造。
- **弹性伸缩**：交易高峰按沙箱扩缩，慢路径可队列化削峰。
- **向量库**：政策库/研报/案例库走本地 Elasticsearch/Milvus（不用默认 Chroma 上生产）。
- **可观测**：每个 `trace_id` 串起一次风控全链路，审计与排障共用。

---

## 7. 诚实边界（这设计该在哪、不该在哪）

1. **这是旁路辅助 + 授信辅助，不是撮合主路径**：AgentScope 负责"风控预警、额度建议、证据化决策"，实际扣款/放行由既有交易系统执行。毫秒级撮合主路径不该直接由 LLM Agent 扛。
2. **一票否决必须可配置**：哪些红线"一票否决"由合规部门定，不能写死在代码里。
3. **阈值/权重是活的**：`GRAY_ZONE`、`N_MULTI`、`hit_rate_weight()` 都要随监管与业务迭代，留痕保证可回溯到"当时用的是哪版规则"。
4. **模型输出需人工最终担责**：高风险授信的"放行"通常仍需人工签核，Agent 给的是**建议 + 证据**，不是终局。

## 8. 结论

信贷风控这个"金融最苛刻"的场景，用 AgentScope 的表达是：

- **双模路由**解耦"毫秒级快路径"与"深度慢路径"，让实时性不被深度推理拖垮；
- **多 Agent 投票**（独立取证 + 加权多数 + 合规/限额一票否决 + 冲突不静默合并）让复杂授信**可解释、可追责**；
- **全链路留痕 + 私有化 + 本地 RAG**满足数据不出域与监管可审计；
- 伪代码把"编排思想"落到 `broadcast / 投票 / 审计` 三块，可直接作为机构定制的起点。

**这正说明：金融能不能用 AgentScope，取决于"用哪个形态 + 怎么用"。用通用版裸奔上核心系统是不该的；用金融版 + 双模 + 投票 + 全链路审计做风控旁路与授信辅助，是被中信证券等多家机构实践验证过的合理用法。**
