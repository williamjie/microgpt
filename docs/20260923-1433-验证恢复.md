# 验证与恢复：从"看起来完成"到"真的完成"

> 本文是 Agent 外壳八大组件系列第 7 篇。总览见 [20260923-1429-Agent本质.md](20260923-1429-Agent本质.md)。

---

## 一、一句话回答

**验证回答"真的完成了吗"，恢复回答"失败之后怎么办"。** 没有这两样，Agent 最大的危险不是报错，而是**把"生成了一个结果"误认为"完成了任务"**——这可能是 Agent 最常见、也最危险的错觉。

2026 年行业趋势也印证了这一点（InfoQ 观察总结）：**失败恢复正在从外围功能变成 Agent 的核心能力**。一个真正可用的 Agent 系统，必须具备的不只是"做事能力"，还包括补证、重试、重规划、阻断、补偿和回滚。

---

## 二、验证：Agent 说"我完成了"，不等于完成

四类"看起来完成"的假象：

- 模型生成了一段总结，逻辑完整，但**事实来源没检查**
- 模型改了一段代码，看起来修好了，但**测试没跑**
- 模型生成了表格，很整齐，但**字段口径不一致**
- 模型说"已完成"，但**目标系统没发生预期变化**

### 验证标准必须来自一开始的目标，而不是模型自己的感觉

| 任务类型 | 看什么 |
|---|---|
| 代码任务 | 测试、类型检查、lint、关键路径 |
| 数据任务 | 行数、字段、口径、异常值 |
| 文档任务 | 结构、事实来源、格式 |
| 操作任务 | 目标系统状态是否发生预期变化 |

战略取舍、品牌表达这类高判断任务，自动验证不够，最终需人类确认。

### 关键设计：验证器与生成器分离

同一个 Agent 写完代码后立刻问自己"是否正确"，容易延续已有假设（它重读自己的代码，觉得"看起来没问题"，然后直接结束——这是 LangChain 团队发现的最常见失败模式）。两种分离方式：

1. **确定性验证器**：测试、lint、类型检查、schema、退出码——不看模型的自我解释
2. **独立上下文评审 Agent**：只看需求、diff 和证据，不读生成过程的自我辩护

**为什么验证重要**：验证不是给 Agent 找麻烦，而是帮它知道**什么时候该停**——没有验证，Agent 要么过早结束（不可靠），要么无限继续（失控）。

## 三、恢复：重试不是机械重复

### 反直觉的第一课

传统代码的 `retry(3)` 对 Agent 不适用。**比喻**：让新厨师做红烧肉，做糊了——传统 retry 是让他用同样方法再做一遍，结果还是糊；Agent 的做法是告诉他"肉糊了，火太大"，让他自己想明白要调小火。

正确流程：工具失败 → 错误信息封装成结构化反馈 → 发给 LLM 分析原因 → LLM 返回调整策略（换参数/换工具/加准备步骤）→ 重新执行。**LLM 能读懂自然语言描述的错误并自我纠正，这是 Agent 系统最核心的优势**——要封装成可复用的错误恢复工具，而不是简单重试。

### 修正策略菜单

临时错误重试；工具不合适就换工具；任务太大就缩小问题；假设被推翻就更新假设；涉及权限/成本/不可逆动作就请求确认；继续做会增加风险就停止。**修正要基于观察结果，而不是基于模型的焦虑**——不能一失败就乱试，要能说清楚"为什么重试、为什么换工具、为什么现在该问用户"。

### 最难的部分：隐性失败

Agent 没报错，但在错误方向上越走越远——后续逻辑完全自洽，解决的却是错误的问题。生产上的三种检测方案：

1. **死循环指纹检测**：对每步 Action 做归一化指纹（工具名+参数键），连续 N 步高度相似即判定循环，强制中断
2. **反思节点**：每执行三步或遇到关键决策，强制发起一次反思调用——"原始目标是什么？已完成哪些？当前动作还指向目标吗？"
3. **独立验证**：见上文验证器分离

### 补偿与回滚

对已执行的错误操作，需要反向冲销（财务场景）、受控回滚（发布场景）、checkpoint 恢复（长任务场景）。**人工介入不是 Agent 失败的羞耻标记，而是风险策略的一部分。**

---

## 四、回到 microgpt

microgpt 的训练循环自带最朴素的"验证"：每个 iteration 打印 loss——**loss 不降就是训练失败的客观信号**，不依赖模型的自我感觉。而训练中断后从 checkpoint 恢复，正是工业级"失败恢复"的最小样本。Agent 系统做的只是把这套"看指标 + 存档点"搬到任务执行层面。
