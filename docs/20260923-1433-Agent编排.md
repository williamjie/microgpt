# Agent 编排：从循环到图

> 本文是 Agent 外壳八大组件系列第 5 篇。总览见 [20260923-1429-Agent本质.md](20260923-1429-Agent本质.md)。

---

## 一、一句话回答

**编排（Orchestration）是超出单个执行循环之后的流程工程：状态怎么跨轮次持久化、独立操作能不能并行、条件分支怎么设计、工具超时怎么办、重试要不要退避、多 Agent 协作会不会死锁。** 它是分布式系统问题，不是提示词问题。

一句话定位（业界共识）：**传统 AgentExecutor 是"模型自己循环玩"，适合 Demo；编排框架是"你编排好流程，模型在里面执行"，适合生产。**

---

## 二、为什么裸循环撑不住？

ReAct 裸循环（见[执行循环](20260923-1433-执行循环.md)）有三个先天短板：

1. **串行执行**：每轮只能调一个工具、等结果再走下一步——5 个互相独立的调用也得排队
2. **无全局状态**：所有信息塞在消息历史里，token 浪费、结构混乱、容易丢失
3. **无法人工介入**：涉及退款、付款、发邮件等不可逆操作时，临时写 if/else 根本扛不住"暂停→保存状态→等审批→恢复→留审计记录"这套完整流程

没有超时机制和循环检测的 Agent，遇到失败任务会**无限重试同一个步骤，把 Token 和钱一起烧光**。

## 三、编排四要素

| 要素 | 解决什么 |
|---|---|
| **流程设计** | Agent 之间的执行顺序与依赖（串行/并行/条件分支/循环） |
| **状态管理** | 维护和传递共享数据，跨轮次持久化 |
| **调度执行** | 控制何时运行哪个 Agent，动态路由 |
| **生命周期管理** | 错误处理、重试、持久化、恢复、终止 |

**比喻**：单个 Agent 循环是一个人闷头干活；编排是给整个团队装上排班表、工单系统、审批流和打卡机。

## 四、主流方案：LangGraph 的图范式

**LangGraph** 是目前工业界复杂 Agent 落地的标准方案（Klarna、Uber、J.P. Morgan、LinkedIn 等生产环境在用），核心思想：把 Agent 建模为**有向图**——节点是操作（LLM 调用、工具执行），边定义流程逻辑。

四个杀手级能力：

1. **全局统一 State**：结构化状态管理，每个节点只更新特定字段，天然支持任务持久化
2. **Checkpoint（检查点持久化）**：每步状态存进数据库（Postgres/SQLite/Redis）——进程崩了能从断点恢复，这带来质变
3. **Human-in-the-Loop（interrupt/resume）**：危险操作前暂停等人工确认，原生支持而不是自己造轮子
4. **子图（Subgraph）封装多 Agent**：Research Agent、Coding Agent、Review Agent 各自成子图，Supervisor 调度

### 多 Agent 协作三种模式

| 模式 | 特点 | 取舍 |
|---|---|---|
| **Handoff** | 交给谁、带什么上下文 | 机制层基础 |
| **Supervisor（监督者）** | 集中调度 | 可控、好调试，慢一点 |
| **Swarm（蜂群）** | 去中心化转交 | 灵活、延迟低，路径难预测 |

### 框架选型一览

| 框架 | 定位 | 短板 |
|---|---|---|
| LangGraph | 图驱动、有状态、生产级持久化 | 学习曲线陡 |
| CrewAI | 角色驱动多 Agent，原型快 | 复杂流程定制难 |
| AutoGen | 对话驱动协作，研究友好 | 生产级持久化弱 |
| Temporal/Prefect | 通用工作流引擎 | 非 LLM 原生 |

## 五、常见坑

1. **Agent 互相转交形成死循环**：A 交给 B，B 交回 A。必须用重试计数和调用上限兜底。
2. **Token 消耗失控**：多 Agent 比单 Agent 链路长、参与者多，token 成本可达聊天模式 15 倍。
3. **共享 State 写冲突**：多个 Agent 同时写同一份状态要互相覆盖——需要 reducer 明确"合并规则"。
4. **过度工程化**：2026 年的行业共识是**从最简单的模式起步**——顺序流水线能解决的事，不要为了炫技上多 Agent。行业里最常见的失败恰恰是过度编排。
